**Two backends, two systems of record, no reconciliation.** `lib/api.ts` is a complete, well-formed
client written against a contract that was never implemented on the server.

### Authentication today

| Path | Mechanism | Where |
| --- | --- | --- |
| Mobile → Cockpit | Entra ID PKCE (`expo-auth-session`) → look up user by MS email in Cockpit; **or** email+password against Cockpit users | `src/lib/auth.ts` |
| Mobile → Cockpit (data) | Shared static API token in `EXPO_PUBLIC_COCKPIT_API_TOKEN` | `src/lib/cockpit.ts` |
| Web → bim-crm | Entra ID authorization-code via Socialite → **session cookie** | `MicrosoftController` |

Note the shared-token pattern: every mobile client carries the same Cockpit API token, so Cockpit
cannot attribute a write to a user or enforce per-user authorization. bim-crm's per-user RBAC is a
material security upgrade, not just a consolidation.

The important architectural property: **the API is a presentation layer, not a second
implementation.** Authorization, numbering, totals, and row-level visibility already exist and are
already tested; the API must route through them rather than re-deriving them. Any endpoint that
bypasses a policy is a defect, not a shortcut.

### Authentication target

⚠️ **SUPERSEDED.** The flow originally drawn here had mobile post the *authorization code* for the
server to exchange. That is wrong for this setup — bim-crm is a confidential client, mobile is a public
PKCE client, and a confidential secret does not apply to a public-client code. The chosen flow has
mobile complete the exchange itself and send the **`id_token`** for server-side validation against
Entra's JWKS. See **D-1b** in `application-design/mobile-architecture.md` for the corrected diagram
and the security constraints.

`expo-auth-session`, `expo-crypto`, and `expo-secure-store` are **already dependencies** on
`cms-integration`, and `src/lib/auth.ts` already implements the PKCE half of this flow against Entra
(`ENTRA_DISCOVERY`, `ENTRA_SCOPES`, `handleAuthCode`). Steps 1–2 are built. Steps 3–9 are the new work.

This resolves the Sanctum-vs-SSO tension in `bim-crm/ai/CONSTRAINTS.md`: the *user* still
authenticates only through Entra ID, and no local password is introduced. Sanctum issues a
**device token after** a successful Entra exchange — it is a session mechanism for a client that
cannot hold a cookie, not a second identity provider.

## Cross-cutting concerns

| Concern | Current | Target |
| --- | --- | --- |
| Transport security | Cockpit over HTTPS; bim-crm behind Traefik, `trustProxies('*')` | Unchanged; API inherits `SecurityHeaders` middleware |
| CORS | Not configured for `api/*` | Must be — Expo Web runs from a browser origin. `api.ts` already anticipates this in `extractNetworkErrorMessage` |
| Error shape | `api.ts` expects `{message, errors:{field:[...]}}` | Laravel's default validation shape — already matches |
| Rate limiting | `throttle` on public quotation routes only | Needs an `api` throttle group; `trustProxies` already makes per-IP buckets correct |
| Offline | `expo-secure-store` + AsyncStorage; no request queue | Q7 in questions file |
| Pagination | Cockpit `limit`/`skip`; `api.ts` expects `{data, meta}` `per_page` | Laravel paginator resources — already matches |
